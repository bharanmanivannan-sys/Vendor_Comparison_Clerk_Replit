CRITICAL BUG: COMPARISON ENTITY CONSISTENCY

We have a serious data-consistency bug in the analysis/executive-summary generation.

USER INPUT:
"Compare Mahindra vs Tata vs MG for EV vehicles"

CURRENT BAD OUTPUT:
- Main page heading correctly says:
  "Compare Mahindra vs Tata vs MG for EV vehicles"
- But Executive Decision incorrectly says:
  "Tata vs MG"
- Recommendation incorrectly says:
  "Tata vs MG"
- Business rationale discusses Mahindra, Tata and MG.
- Immediate actions discuss Mahindra, Tata and MG.

ROOT CAUSE TO FIX:
Different parts of the UI are independently generating/interpreting the comparison entities.

DO NOT PATCH THIS BY SIMPLY CHANGING THE TEXT.
Fix the underlying data flow so that ALL sections derive their comparison identity from ONE canonical comparison object.

==================================================
1. CREATE ONE CANONICAL COMPARISON OBJECT
==================================================

After parsing the user's request, create/use a single canonical object such as:

comparisonContext = {
  originalQuery: "Compare Mahindra vs Tata vs MG for EV vehicles",

  category: "EV vehicles",

  entities: [
    {
      id: "mahindra",
      name: "Mahindra"
    },
    {
      id: "tata",
      name: "Tata"
    },
    {
      id: "mg",
      name: "MG"
    }
  ],

  entityCount: 3,

  comparisonType: "multi_entity",

  displayName:
    "Mahindra vs Tata vs MG"
}

IMPORTANT:
The entities array is the source of truth.

No downstream LLM-generated section is allowed to redefine, remove,
reorder, or replace these entities unless the user explicitly changes
the comparison.

==================================================
2. NEVER RE-PARSE THE QUERY FOR INDIVIDUAL UI SECTIONS
==================================================

Once the query has been parsed:

DO NOT independently ask an LLM to determine:

- headline entities
- recommendation entities
- executive decision entities
- business rationale entities
- action entities
- sidebar entities

All of these must receive the same comparisonContext.

BAD:

generateExecutiveSummary(query)
generateRecommendation(query)
generateHeadline(query)

GOOD:

parsedComparison = parseComparison(query)

generateHeadline(parsedComparison, analysis)
generateExecutiveSummary(parsedComparison, analysis)
generateRecommendation(parsedComparison, analysis)

The parser runs ONCE.

==================================================
3. SEPARATE "COMPARISON SET" FROM "RECOMMENDATION"
==================================================

This is critical.

A comparison can contain:

entities:
["Mahindra", "Tata", "MG"]

while the recommendation can identify ONE entity:

recommendedEntity:
"Mahindra"

These are NOT the same field.

Use a structure similar to:

{
  comparison: {
    entities: ["Mahindra", "Tata", "MG"],
    displayName: "Mahindra vs Tata vs MG"
  },

  recommendation: {
    recommendedEntity: "Mahindra",
    rationale: "..."
  }
}

Therefore:

COMPARISON TITLE:
"Compare Mahindra vs Tata vs MG for EV vehicles"

RECOMMENDATION:
"Mahindra"

EXECUTIVE DECISION:
"Recommended: Mahindra"

DO NOT produce:

"Tata vs MG"

unless the original comparison actually contains only Tata and MG.

==================================================
4. HARD RULE FOR HEADLINES
==================================================

The headline MUST be generated deterministically from
comparisonContext.entities.

For 2 entities:

["Tata", "MG"]
=> "Compare Tata vs MG for EV vehicles"

For 3 entities:

["Mahindra", "Tata", "MG"]
=> "Compare Mahindra vs Tata vs MG for EV vehicles"

For 4 entities:

["A", "B", "C", "D"]
=> "Compare A vs B vs C vs D for EV vehicles"

The LLM must NOT generate or modify this string.

Use a formatter function such as:

formatComparisonName(entities)

and derive all comparison labels from it.

==================================================
5. EXECUTIVE SUMMARY MUST FOLLOW THE SAME RULE
==================================================

The Executive Decision card currently says:

"Tata vs MG"

This is invalid because the comparison contains:

Mahindra + Tata + MG

The Executive Decision heading should instead be something like:

"Recommended: Mahindra"

or:

"Mahindra"

The recommendation may identify the selected/recommended entity,
but it must NEVER silently convert a 3-way comparison into a 2-way
comparison.

==================================================
6. VALIDATION / INVARIANTS
==================================================

Before rendering the page, validate:

A. Every comparison entity exists in comparisonContext.entities.

B. No comparison entity disappears from the comparison title.

C. No new comparison entity can appear in any generated comparison
   label.

D. If entityCount === 3, no section may render a comparison title
   containing only 2 entities.

E. recommendation.recommendedEntity must be one of
   comparisonContext.entities.

F. The recommendation is NOT allowed to redefine the comparison set.

G. The main page heading, executive summary, sidebar and comparison
   metadata must all reference the same comparisonContext.

If validation fails, log a structured error and fall back to the
canonical comparisonContext rather than displaying the LLM output.

8. IMPORTANT NLP RULE
==================================================

Treat:

"vs"
"versus"
"or"
","
"and"
"&"

as possible separators between comparison entities.

For example:

"Mahindra vs Tata vs MG"

MUST resolve to:

[
  "Mahindra",
  "Tata",
  "MG"
]

It MUST NOT resolve to:

[
  "Mahindra",
  "Tata vs MG"
]

or:

[
  "Mahindra",
  "Tata"
]

with MG lost.
