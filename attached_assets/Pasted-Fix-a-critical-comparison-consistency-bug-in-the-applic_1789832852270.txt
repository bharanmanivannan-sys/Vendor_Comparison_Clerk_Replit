==================================================
BUG
==================================================

When the user enters:

"Compare Mahindra vs Tata vs MG for EV vehicles"

the application correctly understands the overall comparison in some sections, but the Executive Decision incorrectly changes the comparison to:

"Tata vs MG"

For example, the current output can contain:

MAIN PAGE HEADING:
"Compare Mahindra vs Tata vs MG for EV vehicles"       ← CORRECT

BUSINESS RATIONALE:
Discusses Mahindra, Tata and MG                          ← CORRECT

IMMEDIATE ACTION:
References Mahindra, Tata and MG                         ← CORRECT

EXECUTIVE DECISION:
"Tata vs MG"                                             ← WRONG

RECOMMENDATION:
"Tata vs MG"                                             ← WRONG

This indicates that different parts of the application are independently
interpreting or regenerating the original user query.

==================================================
CORE REQUIREMENT
==================================================

The user's comparison entities must be parsed ONCE and then treated as
the SINGLE SOURCE OF TRUTH for the entire analysis.

For:

"Compare Mahindra vs Tata vs MG for EV vehicles"

the canonical comparison must be:

entities = [
  "Mahindra",
  "Tata",
  "MG"
]

The system must never silently reduce this to:

[
  "Tata",
  "MG"
]

or any other subset.

==================================================
IMPORTANT DISTINCTION
==================================================

Separate:

1. THE COMPARISON SET
2. THE RECOMMENDATION

Example:

comparison.entities:
[
  "Mahindra",
  "Tata",
  "MG"
]

recommendation.recommendedEntity:
"Mahindra"

The recommendation may select ONE entity from the comparison.

It must NOT redefine the comparison.

Therefore:

VALID:

Comparison:
"Mahindra vs Tata vs MG"

Decision:
"Mahindra"

INVALID:

Comparison:
"Tata vs MG"

Decision:
"Mahindra"

or:

Decision:
"Tata vs MG"

because "Tata vs MG" is not the recommendation; it is an
incorrectly reduced comparison.

STEP 3 — PARSE ONCE
==================================================

The application must NOT do this:

User query
  → LLM parses headline
  → LLM parses recommendation
  → LLM parses executive summary
  → LLM parses rationale
  → LLM parses actions

That creates inconsistent interpretations.

Instead:

User query
  ↓
Canonical comparison parser
  ↓
comparisonContext
  ↓
all analysis/UI sections

The parser should run once per user query.

Downstream LLM calls may analyse the entities, but they must not
redefine the comparison entity set.

STEP 4 — HEADLINE MUST BE DETERMINISTIC
==================================================

The comparison headline must be derived from the canonical entities.

Do NOT allow an LLM to invent or rewrite the comparison title.

Examples:

["Tata", "MG"]
→ "Tata vs MG"

["Mahindra", "Tata", "MG"]
→ "Mahindra vs Tata vs MG"

["A", "B", "C", "D"]
→ "A vs B vs C vs D"

The exact category wording may follow the existing application,
but the entity list must come directly from comparisonContext.entities.

The LLM must never decide that a three-way comparison should become
a two-way comparison.
