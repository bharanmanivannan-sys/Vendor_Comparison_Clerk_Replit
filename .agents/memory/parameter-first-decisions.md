---
name: Parameter-first and evidence-limited decisions
description: How explicit comparison priorities and inconclusive evidence should control scoring and report completion.
---

When a comparison query names a controlling decision parameter, that parameter must drive the research order, deterministic metrics, and scoring weights instead of the generic vendor rubric. Safety-first vehicle decisions require comparable official crash evidence under the same program, protocol/version, score denominator, tested variant, and applicability.

**Why:** Generic weighting rejected a valid Tata Nexon versus Mahindra XUV 3XO safety decision even though authoritative Bharat NCAP evidence existed. The scorer did not recognize crash metrics and required unrelated criteria to reach a generic evidence threshold.

**How to apply:** Detect explicit priorities deterministically, apply a priority-focused weight profile, and register parameter-specific metrics with strict comparability rules. For Indian vehicle safety, seed official manufacturer and Bharat NCAP sources and support stars, adult/child protection, airbags, ESC, and ADAS evidence.

Insufficient deterministic evidence, incomplete source coverage, or an exact scoring tie must not by itself erase a unique pricing/features leader. Preserve a fully supported leader as qualified. If all options remain evidence-insufficient but the available lens rows have one unique leader, show it only as an evidence-limited provisional leader; do not change qualification statuses or imply that neutral 50 scores prove equal performance. If no unique lens leader exists, return the normal executive decision brief with no exact winner and include the required user-discretion warning.

**Why:** A failed job hides useful verified evidence and pressures the system to invent score separation. A previous report found a unique Westpac pricing/feature leader, then a broader evidence gate overwrote it with “No exact winner”; preserving the scoped result keeps the useful conclusion while preventing an overall claim.

**How to apply:** Keep unsupported criteria neutral, do not use arbitrary tie-breaks for explicit-priority decisions, and clearly distinguish provisional, scoped, and overall validated winners. A provisional leader needs an explicit server marker that matches a freshly recomputed unique lens winner; the UI must not show an overall-fit label or score ring. Render the user-discretion warning as bold in browser and PDF outputs.

For capability-led software comparisons, do not give unrequested pricing decision weight. A search-backed, complete feature matrix can support a conditional winner when official evidence covers every option and the transparent row-win calculation has one unique leader.

**Why:** Quantitative-only gates can suppress a clear software capability result even when the requested feature matrix is complete and one option consistently leads.

When a parser adds derived long-horizon or ownership criteria, only activate the price-and-feature lens when the prompt itself names price, cost, budget, or value.

**Why:** A retention period can imply long-term ownership analysis without making price the user's controlling criterion; treating that context as a price request overrides the requested operational priorities.

**How to apply:** Match supplied criteria back to explicit prompt terms before selecting the 65/35 pricing/feature profile. Keep contextual duration and derived ownership labels neutral unless cost is stated.
